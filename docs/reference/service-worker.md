# 서비스 워커

설치 가능하게 만들려고 등록만 하고 아무것도 캐시하지 않는다. 이 문서는 지금 무엇이 어떻게 설정되어 있는지와, 바꿀 때 함께 따라오는 것을 적는다.

## 서비스 워커가 하는 일

브라우저와 서버 사이에서 도는 작은 프로그램이다. 페이지와 별개의 수명을 가지며 페이지가 보내는 요청을 가로챌 수 있다.

보통은 이것으로 캐시를 만든다. 앱의 JS와 CSS를 미리 받아 두고 다음 방문에 서버를 거치지 않고 내준다. 오프라인에서 앱이 열리는 것도 이 방식이다.

## 지금 설정

`vite.config.ts`의 `VitePWA` 옵션이다.

```ts
workbox: { globPatterns: [], navigateFallback: null }
```

| 옵션 | 값 | 뜻 |
| --- | --- | --- |
| `globPatterns` | 빈 배열 | 미리 받아 둘 파일이 없다 |
| `navigateFallback` | `null` | 페이지 이동을 캐시된 HTML로 돌리지 않는다 |
| `registerType` | `autoUpdate` | 새 서비스 워커가 나오면 바로 교체한다 |

결과로 캐시되는 것과 되지 않는 것은 이렇다.

| | 내용 |
| --- | --- |
| 캐시한다 | `manifest.webmanifest`, 아이콘 4개. 합쳐 1KB 미만 |
| 캐시하지 않는다 | HTML, JS, CSS, API 응답, 영상 정보 |

앱 코드를 캐시하지 않으므로 오프라인에서 열면 그대로 실패하고, 새로고침하면 늘 서버에서 최신 배포본을 받는다.

manifest와 아이콘은 플러그인이 자동으로 목록에 넣으며 이 동작은 끌 수 없다.

## 캐시하지 않는 이유

[M-05](https://github.com/Dynamic-Juo/docs/blob/main/project/mvp-review.md)에서 서비스 워커 기반 오프라인 캐시와 별도 업데이트 처리를 제외했다. 근거는 둘이다.

영상 수집, 모델 분석, 근거 검색이 모두 서버를 거쳐야 해서 오프라인에서 할 수 있는 일이 없다.

캐시를 두면 새 배포본이 나왔는데 옛 화면이 보이는 상황을 따로 다뤄야 한다. 캐시 버전 관리, 갱신 알림, 서비스 워커 교체 시점이 모두 따라온다.

## 그런데도 등록하는 이유

Chromium은 설치 가능 여부를 판단할 때 `fetch`를 처리하는 서비스 워커를 요구한다. 없으면 `beforeinstallprompt`가 발생하지 않아 설치 진입점을 띄울 수 없다.

지금 서비스 워커는 등록만 되고 가로채서 하는 일은 없다.

## 개발 서버에는 없다

`vite-plugin-pwa`는 빌드에서만 `index.html`에 manifest 링크를 넣고 서비스 워커를 만든다. 개발 서버에서 `manifest.webmanifest` 주소를 직접 열면 파일은 나오지만 HTML이 가리키지 않아 브라우저가 설치 대상으로 보지 않는다.

`devOptions`로 개발 서버에서도 켤 수 있지만 쓰지 않는다. 개발 중에 서비스 워커가 돌면 고친 코드가 화면에 반영되지 않는 상황이 생긴다. 설치 동작은 배포본에서 확인한다.

## 확인하는 곳

Chrome 개발자도구의 `Application` 탭이다.

| 항목 | 볼 것 |
| --- | --- |
| `Manifest` | 아이콘 미리보기, 설치 가능 여부, 빠진 조건 |
| `Service Workers` | 등록과 활성 상태 |
| `Cache Storage` | 실제로 저장된 파일. `index.html`이나 `assets/*.js`가 보이면 설정이 잘못됐다 |

## 바꿀 때

오프라인 캐시를 넣기로 하면 다음이 함께 필요하다.

- 캐시할 파일 목록과 갱신 기준
- 새 배포본이 나왔을 때 사용자에게 알리고 새로고침을 받는 흐름
- 서비스 워커 교체 시점 처리. 열려 있는 탭이 여럿일 때 어느 버전이 도는지
- API 응답을 캐시할지. 분석 결과는 서버에도 남지 않으므로 캐시하면 사라진 결과를 보여줄 수 있다

M-05를 다시 열어야 하는 변경이다.
