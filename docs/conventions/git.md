# 커밋과 브랜치 규칙

커밋 메시지와 브랜치 이름 규칙이다. 유형은 둘이 같은 목록을 쓴다.

## 유형

| 유형 | 커밋 | 브랜치 | 쓰는 때 |
| --- | --- | --- | --- |
| `feat` | `feat(ui):` | `feat/` | 사용자 또는 시스템에 새 기능을 추가한다 |
| `fix` | `fix(api):` | `fix/` | 잘못된 동작을 수정한다 |
| `refactor` | `refactor(ui):` | `refactor/` | 동작을 유지하면서 구조를 변경한다 |
| `docs` | `docs(repo):` | `docs/` | 문서와 시안만 변경한다 |
| `test` | `test(domain):` | `test/` | 테스트를 추가하거나 수정한다 |
| `perf` | `perf(ui):` | `perf/` | 성능을 개선한다 |
| `build` | `build(repo):` | `build/` | 빌드 시스템이나 의존성을 변경한다 |
| `ci` | `ci(repo):` | `ci/` | 배포와 자동화 설정을 변경한다 |
| `chore` | `chore(repo):` | `chore/` | 위에 해당하지 않는 유지보수 작업이다 |

여러 유형이 섞이면 주목적을 기준으로 고른다. 목적이 다르면 커밋을 나눈다.

## 커밋 제목

Conventional Commits 형식을 사용하고 scope를 반드시 포함한다.

```text
<type>(<scope>): <요약>
```

요약은 변경 결과를 나타내는 한국어로 작성하고 마침표를 붙이지 않는다.

## 범위

아래 목록에서만 선택한다. 동의어나 새 범위를 임의로 쓰지 않는다. 새 범위가 필요하면 이 목록에 정의한 뒤 사용한다.

| scope | 적용 범위 |
| --- | --- |
| `repo` | 저장소 운영, 빌드·린트·배포 설정, 기준 문서 |
| `ui` | 화면, 컴포넌트, 스타일, 라우팅 |
| `api` | 서버 연동, 요청·응답 처리, mock |
| `domain` | 프레임워크에 의존하지 않는 도메인 타입과 순수 로직 |
| `wireframes` | 와이어프레임과 시안 파일 |

폴더 이름이 아니라 변경의 목적을 기준으로 고른다. 여러 범위를 함께 수정하면 주목적을 기준으로 선택한다.

## 본문

제목만으로 드러나지 않는 이유를 설명할 때 작성한다. 파일 목록을 반복하지 않는다. 검증을 수행했다면 실제 실행한 검사만 기록한다.

하이픈 목록으로 쓴다. 한 항목에 한 주제만 담고, 여러 주제를 한 문단에 이어 붙이지 않는다. 무엇을 바꿨는지와 왜 그렇게 했는지를 같은 항목에 적는다.

작성자 정보나 도구 서명을 트레일러로 추가하지 않는다.

## 커밋 예시

```text
feat(ui): 주장 카드 목록과 진행률 표시 추가
feat(domain): 분석 작업 상태와 검증 판정 타입 정의
build(repo): vanilla-extract 설정
docs(wireframes): 한국어가 아닌 영상의 처리 반영
```

본문까지 쓰면 이렇다.

```text
feat(api): 분석 작업 폴링 훅 추가

- 최종 상태 네 가지에서 폴링을 멈춘다. 서버가 종료된 작업에도 200을 주기 때문에 응답만으로는 멈출 시점을 알 수 없다.
- 간격은 2.5초로 뒀다. API 계약이 권장하는 값이다.
```

## 브랜치

작업 브랜치는 `main`에서 분기하며 위 표의 접두사를 붙인다.

```text
<type>/<주제>
```

주제는 영문 소문자와 하이픈으로 쓴다. 브랜치 이름만 보고 무엇을 하는 작업인지 알 수 있어야 한다.

- 하나의 브랜치와 PR에는 함께 검토할 변경만 포함한다.
- 독립적인 PR은 같은 기준의 `main`에서 분기해 서로의 변경을 포함하지 않는다. 의존 관계가 있으면 PR 본문에 명시한다.
- 병합한 브랜치는 지운다. 원격에 남겨 두면 어느 것이 진행 중인지 알 수 없다.
